# 一刻相册原图导出

## Role

把用户一刻相册里的照片和视频**以字节级原图**完整搬到本地磁盘。核心承诺是可验证：每个文件下载后用云端返回的 MD5 比对，只有一致才算成功。

## Context

- 接口是**非官方**的（`photo.baidu.com` 网页端接口），百度可能随时调整。字段或路径变化时以 `scripts/yike_export.py` 中的 URL 为准去核对，不要凭记忆改。
- **绝不索取账号密码**。认证只复用用户已登录浏览器的 Cookie。这是唯一的凭据来源，也是唯一的合规姿势。
- 用户的数据量可能很大（几万张、上百 GB）。默认行为必须是保守的：先盘点、再试跑、最后全量。
- 不做任何写操作。本工具只有读取、写本地文件，以及清理自己的 `.part` 临时文件三类动作，永远不会调用删除云端文件的接口。

## Capabilities

- 检查 Cookie 是否有效，统计云端项目总数、照片/视频分布与总容量。
- 导出完整清单（JSONL + CSV），用于迁移前盘点、去重分析或留档。
- 列出所有相册及各自项目数，支持只导出指定相册。
- 流式下载原图/原视频，边下边校验 MD5，失败自动重试。
- 断点续传：中断或 Cookie 过期后重跑同一命令，只补未完成的项。
- 相同内容去重（默认硬链接），避免同一张图在多个相册里重复占空间。
- 按 `flat` / `year` / `year-month` 归档，并还原文件的拍摄时间戳。
- 独立校验已下载文件的 MD5，随时证明本地副本与云端一致。

## Instructions

### 1. 先确认三件事

在动手前确认：

1. **目标目录**：建议独立空目录（如 NAS 挂载点或移动硬盘）。必须确认剩余空间 ≥ 云端总容量 × 1.2。
2. **数据规模**：先跑 `check`，拿到项目数和总容量再决定策略。
3. **是否要全量**：用户可能只想导出某个相册，或只要照片不要视频。

### 2. 认证：引导用户取 Cookie

首选浏览器自动读取（最省事）：

```bash
pip install requests browser_cookie3
python3 scripts/yike_export.py check --browser chrome
```

失败时改手动方式，让用户在**已登录一刻相册的浏览器**里按 F12 → Network → 任意 `photo.baidu.com` 请求 → 复制请求头里的完整 `Cookie`：

```bash
python3 scripts/yike_export.py check --cookie-file cookies.txt
```

关键字段是 `BDUSS`（登录态）和 `STOKEN`。缺这两个必然失败。

**安全提醒**：Cookie 等同于账号登录态。提醒用户用完即删 `cookies.txt`，不要提交进 git，不要发给别人。工具本身不落盘 Cookie。

### 3. 标准执行顺序

```bash
# 第 1 步：验证凭据 + 盘点规模（只读，不下载）
python3 scripts/yike_export.py check --browser chrome

# 第 2 步：小批量试跑，确认命名和目录结构符合预期
python3 scripts/yike_export.py download --browser chrome \
    --out /Volumes/Backup/yike --limit 20 --dry-run

# 第 3 步：真正试跑 20 项
python3 scripts/yike_export.py download --browser chrome \
    --out /Volumes/Backup/yike --limit 20

# 第 4 步：全量下载（可随时 Ctrl-C，重跑即续传）
python3 scripts/yike_export.py download --browser chrome \
    --out /Volumes/Backup/yike --jobs 4 --layout year-month

# 第 5 步：校验完整性
python3 scripts/yike_export.py verify --out /Volumes/Backup/yike
```

### 4. 参数选择

| 场景 | 参数 |
|---|---|
| 只要某个相册 | `--album <ID>`（ID 从 `albums` 子命令取） |
| 按年月归档，便于人工浏览 | `--layout year-month` |
| 只要照片不要视频 | 先 `list` 导出清单，再按扩展名筛选 |
| 网络不稳/怕风控 | 降 `--jobs 2`，加 `--sleep 1` |
| 磁盘紧张 | 保持默认 `--dedup link`（硬链接不额外占空间） |
| 迁移到不支持硬链接的文件系统 | `--dedup copy` |
| 分页异常但仍要处理已有清单 | `--allow-partial`（见下方"分页完整性"） |

### 5. 分页完整性：本工具最重要的安全设计

接口用游标分页。如果服务端声称"还有下一页"却给出空游标或重复游标，**把它当成末页是
最危险的**——用户会拿到一份不完整的备份，却以为已经导出完毕。

本工具的处理方式：

1. 检测到这种异常时，**在下载开始前就中止**，退出码 `1`，并明确打印警告。
2. `check` / `list` 会标注总数只是下限（"至少 N 项"），不会谎报为完整统计。
3. 确实需要在已知不完整的情况下继续，显式加 `--allow-partial`，此时警告依然打印。

**agent 注意事项**：看到"清单可能不完整"的警告时，不要告诉用户"导出完成了"。
应该说明只处理了多少项、为什么可能漏，并建议重跑一次再确认。

### 6. 同名文件与重复运行（另一类静默失败）

多台相机、多个目录都会产出 `IMG_0001.jpg` 这种同名文件。云端清单的**返回顺序会变**
（新增照片插队、改 `--limit`、切 `--album` 都会造成）。

工具的处理原则：**一个磁盘路径一旦被某个文件认领，就绝不再分配给别的文件**，
且只在**云端 MD5 逐字节校验通过**时才认为本地文件可用（只比大小是不够的——
两台相机拍出的同名照片经常同为 4096 字节，但那不是同一张图）。

因此：

- 续传时优先沿用状态记录里的原路径，不按本轮顺序重新分配名字。
- 目标文件名被内容不同的既有文件占用时，新文件另存为 `名字 (1).jpg` 并打印警告，
  **绝不覆盖**用户已有的文件。
- 去重（硬链接/复制）前会先校验源文件内容；不符则退化为真实下载。

看到"目标文件名已被内容不同的既有文件占用"的警告时，告诉用户这是正常的保护行为，
并说明新文件的实际名字。

### 7. 判断结果

- 退出码 `0` 全部成功；`1` 有失败项、分页异常或清单为空（重跑即只重试失败项）；`2` Cookie 失效（重新登录后重跑）；`3` 参数或环境问题。
- 每次运行写 `yike-export-report.json`，含失败明细。
- **只有在无分页警告、无失败项、且 `verify` 通过时**，才能对用户说"已完整导出"。

### 8. 删除云端副本前的安全前提

`verify` 通过只证明**当时**磁盘上的文件与云端一致，**不保证以后仍然如此**。以下顺序才算安全：

1. 全量下载完成，无失败项、无分页警告。
2. 跑一次 `verify`，退出码为 `0`（有文件缺失或无法校验时它会返回非 0）。
3. **再次运行下载**（此时应为"跳过全部、新下载 0"）并**再 `verify` 一次**，
   确认没有出现新增文件导致的重新分配。
4. 确认无误后，才考虑清理云端。

原因：云端清单会变（新照片插队、服务端重排）。工具的续传逻辑已保证"同名文件
不会被覆盖"，但用户仍应完成上面第 3 步再删云端——这是唯一能发现历史错绑的时机。

## 边界与风险

- **必须如实告知用户**：这是非官方接口。百度改协议时工具会失效，需要更新 `scripts/yike_export.py` 里的接口路径与字段名。
- **不要把 MD5 一致说成"绝对没被压缩"**。MD5 证明的是本地文件与云端返回的字节完全一致。如果云端存的就是压缩过的版本，本工具无法识别——这需要用户自己在网页端对比下载同一张图来判断。
- **并发别开太高**。`--jobs` 超过 8 有被限流甚至临时封禁的风险，默认 4 是稳妥值。
- **Cookie 过期**在长时间下载中很常见。此时进度已保存，重新登录后重跑即可，不要从头开始。
- **磁盘空间**：下载前务必确认。填满系统盘会连累整机。
- **报告可安全分享**：工具会把 `dlink` 签名和 `bdstoken` 从错误信息中裁掉再写盘。
  即便如此，也提醒用户 `yike-export-report.json` 含本地文件路径，公开前自行判断。
